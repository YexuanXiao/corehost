**你的任务：重构 openconsole**

请严格遵循以下所有规则与约束，逐步完成 openconsole 项目的重构，重构后的项目名是 corehost。所有改动必须符合这些要求，不可遗漏任何细节。

### 构建与工具链
- 代码必须在以下三个编译器下编译通过并正常工作：**MSVC**、**Clang**、**Clang-CL**。
- 语言标准统一采用 **C++23**。

### 错误码与异常
- 使用强类型 `enum class` 表示错误码，**禁止**使用 Win32 原始的整数类型错误码。
- 使用 C++ 异常直接抛出上述 `enum class` 错误码。**仅在确有必要时**才捕获异常，其余情况让异常自动向上传播。

### 字符串与视图
- 若需要“以 0 结尾的宽字符字符串视图”，请使用 `win32::wcstring_view` 而不是 `wchar_t*`。
- 若不需要 0 结尾，则使用 `std::wstring_view`。

### GUI 与 Unicode
- Unicode 处理**只能**使用 `utf_view` 或 **libunicode**，不得使用其他方式。

### 标准库使用限制
- 尽量使用 C++ 标准库，但明确**禁止使用**以下标准库组件（测试无限制）：
  - `<filesystem>`
  - `<thread>`（允许 `<atomic>`）
  - `<expected>`
  - `<locale>`
  - `<exception>`
  - `<iostream>`

### Win32 错误处理
- **严格处理所有 Win32 函数调用结果**。任何 Win32 函数失败时，必须获取其强类型错误码，并据此抛出异常或终止程序，不得忽略或吞没错误。

### 新文件组织与格式
- 新的实现按功能进行细致分类。

### 重构策略与过程要求
- 执行**渐进式重构**，要求同时满足：
  - 从 `main` 函数开始重构，逐步深入到最底层的调用。
  - **精简程序状态**：尽可能减少全局和静态变量，将它们转换为函数参数沿调用链传递。追踪每个全局变量的使用路径，逐步通过参数注入替代全局访问。
- 重构过程中**必须积极地反复进行构建和测试**。每次修改后尽快编译并运行相关测试，确保尽早发现问题。
- 如果任何测试失败，**你必须为代码添加更多的诊断信息**（如日志输出、状态打印、断言消息等），以便定位问题，然后修复并重新测试，直到通过。
- 你需要**编写重构计划**，并在关键决策点**记录你的决策过程**（例如通过注释或单独的计划文件说明为何选择某种实现方式、为何推迟或放弃某些重构）。
- 重构的同时**清理旧代码**，移除不再需要的注释掉的代码、冗余逻辑，并为新代码**添加解释调用流程和功能的注释**，提高可读性。注释应说明代码的意图、关键步骤和设计选择，而不是简单复述代码。

### 编码禁止事项
- **禁止使用虚函数**（virtual functions），除了COM。
- **禁止使用 WIL 宏**，若有类似功能需要，请自己设计帮助函数（helper functions）。

### 转换与算法
- 进行窄化转换时，必须使用 `utility::narrow_cast`。
- 遍历与处理数据时，优先使用**范围 for 循环**和**标准库算法**。

### 编译错误检索
- 遇到编译错误时，**只搜索项目内的文件** 来定位问题，禁止搜索项目外部的系统库或外部依赖文件。

### 设计风格与RAII
- 所有自行封装的 API 都应遵循 **C++ 标准库风格** 并使用 **RAII** 管理资源（测试不需要）。
- 禁止使用不是默认删除器的 `std::unique_ptr`，为其他删除器设计各自的类，并编写析构函数。
- 格式化字符串统一使用 `std::format`，不得使用 `fmt` 库。
- 禁止使用静态成员函数。
- 禁止使用内部链接。

### 外部依赖约束
- 如果你在重构时遇到一个复杂需求，或者需要一个高质量实现，且似乎必须引入外部库才能解决，**请立即停下来，向我请求帮助**，不要自行引入。
- 重构后的代码应**避免依赖 oss 文件夹下的库**。

### 学习与一致性要求
- **中已有的文件**（包括 `third_parties` 子目录）是你需要学习和使用的代码参考。你重构后的代码在风格、结构和实现方式上应**与这些现有文件保持一致**。

### 代码修改范围

- 除了 `third_parties` 目录外，所有代码都是可修改的。

### 测试要求
- 你必须为新重构的代码编写测试。
- 测试运行前必须**禁用 Windows CRT 的 debug 弹窗**（例如设置 `_CrtSetReportMode` 等），避免测试被对话框阻塞。
- 测试分为两种方式进行：
  1. **独立单元测试**  
     对于不需要和外部交互的功能（纯逻辑、数据结构、工具函数等），独立对该功能进行测试，不依赖 corehost 主程序。
  2. **程序交互测试（集成测试）**  
     对于其他较复杂的情况，编写一个测试程序，该程序与 corehost 程序进行交互。  
     - 在 corehost 程序内部合适位置插入**检查点**，通过读取环境变量来进入测试模式。  
     - **不同环境变量值代表不同的测试项目**，程序根据该值执行对应的测试路径并输出或反馈结果。  
     - 测试程序启动 corehost 并设置相应的环境变量，以驱动指定测试场景并验证行为。

### 字符串传递与中间构造
- **禁止不必要的临时字符串构造**。如果函数接受 `PCWSTR` 且已有字符串视图（如 `win32::wcstring_view`），请直接调用 `.c_str()` 传递，不得构造 `std::wstring` 作为过渡。`std::wstring` 仅应在确实需要深拷贝或修改副本时使用。重构过程需要积极使用 `win32::wcstring_view` 代替 `wchar_t*` 和 `PCWSTR`。

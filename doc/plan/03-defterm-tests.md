# 计划 C：defterm 自动化测试

## 1. 背景

defterm（默认终端）形态下，corehost 被系统作为控制台宿主拉起，拿到 ConDrv
会话后通过 COM handoff 把会话交给默认终端（通常是 WindowsTerminal），自己
留在后台转发信号。现有测试几乎只覆盖 conpty（libconpty 创建伪控制台）路径，
defterm 的启动、handoff、窗口交互、关闭语义都没有自动化覆盖。

defterm 是用户最常见的入口（双击控制台程序），它出问题的影响面最大。

## 2. 测试目标

1. defterm 入口能稳定完成"启动控制台程序 → handoff 到终端 → 交互 → 关闭"。
2. 控制台功能在 defterm 下与 conpty 下一致（同一套断言可复用）。
3. 伪窗口（阶段 B）在真实终端环境下可用：`GetConsoleWindow` 返回的句柄能收
   消息，关闭语义正确。
4. 子进程/继承控制台行为正确：进程列表、共享控制台、退出码、`Ctrl+C`。
5. 全部用例可用一条命令自动执行，失败可定位，不污染用户环境。

## 3. 关键挑战与策略

| 挑战 | 策略 |
| --- | --- |
| defterm 由系统拉起，无法直接在测试进程里"调用" | **不修改任何系统设置**：测试进程自己扮演控制台客户端——`NtCreateFile` 打开 `\Device\ConDrv\Server` + `\Reference`，用 `corehost.exe <handle>` 启动 defterm 入口，再打开 `\Connect`（EA 携带 `CONSOLE_SERVER_MSG`）并把连接写入 PEB ConsoleHandle |
| 真实终端（WT）行为依赖版本、安装、主题、动画 | 环境探测（安装/版本/会话可见性）；不满足时用例标记 SKIP 并输出原因，不计为通过 |
| 终端窗口是 GUI，输入注入不稳定 | 优先用控制台 API / VT 序列驱动（客户端程序内部执行），GUI 消息只用于窗口语义用例 |
| 时序不确定（启动、handoff、首帧） | 所有等待都有截止时间 + 轮询间隔；超时输出会话侧日志与进程状态快照 |
| 系统状态污染（注册表、CLSID、窗口、进程） | 用例不写注册表、不改默认终端；每个用例独立进程/独立会话，结束后清理进程与窗口 |
| 无第三方测试框架（禁止联网） | 使用 `design/0003` 的自研测试库 |

## 4. 测试库设计（C1）

一个可以被 C、D 两个阶段共用的测试库，包含：

1. **runner**：用例注册、过滤（按标签/名称）、逐用例隔离执行、超时、汇总
   报告、退出码。风格参考流行框架（`TEST_CASE`/`REQUIRE`/`CHECK` 语义）。
2. **会话驱动**：启动/停止被测控制台进程；获取退出码；等待输出出现；
   超时与取消；收集诊断。
3. **控制台客户端**：一个测试用的控制台程序，按脚本执行 Console API / VT
   序列 / 窗口消息，并把结构化结果写到约定位置（stdout 或临时文件）。
4. **终端状态断言**：对输出流做最小 VT 解释（文本、光标、SGR、清屏），支持
   "最终屏幕"断言，而不是脆弱的字节序列匹配。
5. **环境探测**：WT 是否存在与版本、是否交互式会话、sshd 状态、可用 shell、
   vim/edit 路径；统一以"前置条件"形式表达。
6. **诊断**：失败时输出会话日志、客户端日志、窗口状态、运行时长、完整输出
   流（截断保护）。

约束：测试库本身必须有测试（至少覆盖 runner、断言、超时、跳过语义）。

## 5. 用例矩阵（最低覆盖）

| 组 | 用例 |
| --- | --- |
| 启动/handoff | 启动 cmd/powershell/pwsh 成功；首屏出现提示符；退出码正确；连续启动 3 个会话互不影响 |
| 控制台功能 | 屏幕尺寸与 `GetConsoleScreenBufferInfo`；光标移动；颜色属性；标题设置/读取；代码页与 Unicode 输出；`ReadConsole` 输入回显 |
| 窗口功能 | `GetConsoleWindow` 非 NULL；`IsWindow`；`GetWindowRect` 合理；`SendMessageTimeout(WM_...)` 不超时；`WM_CLOSE` 结束会话；最小化/显示调用不崩溃 |
| 输入 | 键盘字符、退格、方向键、功能键、`Ctrl+C`/`Ctrl+Break`、`Ctrl+Z`；粘贴多字节文本 |
| 子进程/继承 | 子进程继承控制台并读写；`GetConsoleProcessList` 含父子、退出后移除；子进程退出码；父进程退出时子进程行为 |
| 关闭 | 客户端主动退出；发 `WM_CLOSE`；终端进程被杀；关闭事件投递（`CTRL_CLOSE_EVENT`） |
| 异常 | 非法 API 参数返回错误而不崩溃；超大输出；快速开关会话 20 次无泄漏 |

每个用例标注：标签、前置条件、超时、是否可在 CI 无头环境运行。

## 6. 真实终端 vs 确定性替身

defterm 测试必须覆盖"真实 WT"，但真实 WT 的启动/窗口/版本让 CI 很脆弱。因此
用例分三层：

- **L0 直连层**：测试进程自建 ConDrv 会话并直接驱动 defterm 入口（`\Connect`
  + PEB ConsoleHandle），验证 CONNECT、控制台 API、子进程继承、退出语义。
  不依赖注册表/默认终端/GUI，默认在 CI 运行。
- **L1 确定性层**：用一个测试实现的 handoff 接收方（COM 服务器）代替 WT，验证
  corehost 的 handoff 协议、信号转发、退出语义。
- **L2 真实终端层（已删除）**：曾有机会式冒烟 `Defterm.RealTerminal`，但它依赖
  用户默认终端、会在桌面真实弹窗且无法在 CI 稳定运行；按决定删除。defterm 的
  覆盖保留 L0 直连（`Defterm.Connect`）与 L1 替身（`Defterm.Handoff`、
  `Defterm.ClientNotify`）。
  需要交互式会话 + 已安装 WT，探测不到则跳过。

两层共用同一套控制台客户端与断言。任务要求"和 WindowsTerminal 进行交互"，
因此 L2 是验收必需项，但 L1 保证日常回归的确定性。取舍记录在 `design/0003`。

## 7. 实施顺序

| 编号 | 子任务 | 产出 |
| --- | --- | --- |
| C1 | 测试库骨架：runner/断言/隔离/超时/环境探测 + 自测 | 测试库 + 自测 |
| C2 | 进程与会话驱动；诊断收集；ConDrv 客户端 | 驱动 + 自测 |
| C3 | defterm 启动路径：delegation 指向 corehost、启动客户端、等待就绪 | 可运行的冒烟用例 |
| C4 | 控制台测试客户端（脚本化 API/VT/窗口消息） | 客户端程序 + 用例 |
| C5 | 用例矩阵实现：控制台/窗口/输入/子进程/关闭 | 用例集 |
| C6 | 真实 WT 层（L2）与稳定性（重复 3 次、无残留）+ 文档 | 通过记录 + board |

C1 是 D 的前置；C3 依赖阶段 B 的窗口；C6 依赖 B6/B7。

## 8. 验收标准

1. `ctest` 中新增 defterm 测试组可通过一条命令执行；不满足环境前置的用例
   显示 SKIP 及原因。
2. 同一套用例连续执行 3 次，结果一致；失败时能仅凭产物定位（日志/输出/窗口
   状态）。
3. 用例结束后：无残留 `corehost.exe`/终端进程、无残留窗口；全程不触碰注册表与
   系统设置（代码审查 + 运行前后 `%%Startup` 值不变）。
4. 真实 WT 用例至少覆盖：启动、输出可见、`GetConsoleWindow`、`WM_CLOSE`、
   子进程继承。
5. 测试库自身有覆盖：runner 的通过/失败/超时/跳过路径各有用例。

## 9. 风险与开放问题

- 修改 `HKCU\Console\%%Startup` 会影响用户当前会话的所有新控制台。必须提供
  显式开关（环境变量/参数）默认不启用；启用时保证异常恢复。是否需要以及如何
  做"只影响测试会话"的隔离（例如用不同用户、容器、独立 session）待评估。
- WT 版本差异导致窗口结构不同（UIA 树、标题）。L2 用例应尽量用控制台 API
  断言，窗口只断言"能收消息"与"关闭生效"。
- 测试客户端本身是控制台程序，它的 `GetConsoleWindow` 依赖阶段 B 的实现；
  B 未完成时相关用例要能单独跳过而不是整组失败。
- 无头 CI（无交互式桌面）无法跑 L2：需要在 CI 配置中显式区分，避免"静默全绿"
  掩盖真实缺口。

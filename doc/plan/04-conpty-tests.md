# 计划 D：conpty 自动化测试

## 1. 背景

现有 conpty 测试（`tests/`）覆盖了换行、键盘、光标同步、WriteConsole 光标、
PowerShell 错误颜色、edit 真实交互等，但整体是"单场景脚本 + 字节匹配"：
每个测试自建 ConPTY、自写期望字符串，缺少统一会话驱动、屏幕状态断言和失败
诊断；也没有覆盖 ssh 远程连接、子进程继承控制台等组合场景。

## 2. 测试目标

1. conpty 会话的建立/输入/输出/resize/clear/EOF/退出码全部可自动化验证。
2. 用真实程序（cmd、powershell、vim、edit）验证交互行为，而不只是 VT 序列。
3. 覆盖 ssh 远程组合：ssh 客户端 ↔ 本机 sshd 的远程 pty，验证远程程序在
   conpty 下工作。
4. 覆盖子进程继承控制台：子进程读写、进程列表、并发输出、退出传播。
5. 所有用例一条命令执行，失败可定位，重复执行结果稳定。

## 3. 测试库设计（D1）

与 C1 共用 runner、断言、隔离、诊断。conpty 特有的部分：

1. **会话驱动**：创建伪控制台（多种尺寸、flag 组合）、输入写端、输出读端、
   信号通道（resize/clear/reparent）、关闭；所有等待带截止时间。
2. **输出泵**：后台线程持续读输出，避免管道写满导致被测程序阻塞；同时按时间
   顺序保存原始流供断言与诊断。
3. **VT 屏幕模型**：最小解释器（文本、CR/LF、CUP、ED/EL、SGR、DECSTBM、
   备用屏幕），提供"等待屏幕包含/等于某状态"的断言，替代原始字节匹配。
4. **进程控制**：启动被测程序（带属性列表）、等待退出、取退出码、超时终止、
   子进程枚举、进程树清理。
5. **前置条件**：vim/edit 路径、sshd 服务状态、可用 shell、字体/宽度假设。

## 4. 用例矩阵（最低覆盖）

| 组 | 用例 |
| --- | --- |
| 会话生命周期 | 创建/关闭；尺寸 1x1、80x25、超大；`PSEUDOCONSOLE_INHERIT_CURSOR`；重复创建 20 次无泄漏 |
| 输出 | ASCII/中文/emoji/组合字符；多行滚动；超长行；大批量输出不丢字节；`\r` 覆盖写 |
| VT 序列 | CUP/CUU/CUD/CUF/CUB、ED/EL、SGR（16/256/truecolor）、OSC 标题、DECSTBM、备用屏幕切换 |
| 光标 | CPR 继承、WriteConsole 光标追踪、回车换行、自动换行边界 |
| 输入 | 字符、退格、方向/功能键、`Ctrl+C`/`Ctrl+Break`、`Ctrl+Z`、Win32 Input Mode、粘贴大段文本 |
| resize/clear | ResizePseudoConsole 后尺寸生效、内容重排；ClearPseudoConsole 行为；连续 resize 不崩溃 |
| 真实程序 | cmd 命令输出；powershell/pwsh 交互与错误着色；vim 打开/编辑/保存/退出；edit 打开/编辑/退出 |
| ssh 远程 | 本机 sshd + ssh 客户端建立远程 pty；远程执行命令并回显；远程交互程序（如远程 powershell/cmd）；断开连接后会话结束 |
| 继承控制台 | 子进程读写同一控制台；`GetConsoleProcessList`；父子同时输出不交错；子进程退出码；父进程退出后子进程行为 |
| 异常 | 非法尺寸；关闭后继续写；写端断开；读端不读（输出泵验证不阻塞）；被测程序崩溃 |

每个用例标注标签、前置条件、超时、稳定性级别。

## 5. ssh 组合的具体设计

前提（探测，不满足则跳过）：

- 本机 `sshd` 服务已安装并可启动；允许用普通用户 + 公钥登录回环地址；
- 端口不与现有服务冲突（使用测试专用端口，例如从高位区间挑空闲端口）；
- 只使用 `ssh.exe`/`sshd.exe`（系统自带），不依赖 bash。

流程：测试启动一个专用 sshd 实例（独立配置/端口/授权文件，结束即清理）→
用 `ssh -tt` 连接 → 远端执行被测程序（cmd/powershell/简单控制台探针）→ 通过
conpty 输出断言交互 → 断开后断言会话结束、进程清理干净。

安全与隔离：不复用用户已有 `~/.ssh` 配置与 known_hosts；测试专用临时目录；
不修改系统 sshd 配置；失败时也要杀死自己启动的进程。

## 6. 实施顺序

| 编号 | 子任务 | 产出 |
| --- | --- | --- |
| D1 | 测试库：会话驱动、输出泵、VT 屏幕模型、诊断 | 测试库 + 自测 |
| D2 | 控制台测试程序（脚本化 API/VT/子进程操作） | 客户端 + 用例 |

| D4 | 真实程序用例：cmd、powershell、vim、edit | 用例集 |
| D5 | ssh 远程组合：专用 sshd + 连接 + 远程交互 + 清理 | 用例集 |
| D6 | 子进程继承用例 + 稳定性（重复 3 次、无残留）+ 文档 | 通过记录 + board |

D1 依赖 C1 的 runner；D4 与 D5 可以并行；D6 依赖 D2/D3。

## 7. 验收标准

1. `ctest` 中 conpty 测试组可通过一条命令执行；每用例独立会话、独立超时。
2. 每个用例重复 3 次结果一致；不依赖固定 `sleep`，等待都是"条件 + 截止时间"。
3. 失败产物足以定位：完整输出流、屏幕快照、会话日志、进程状态、退出码。
4. ssh 用例在环境具备时真实执行（不是 mock），结束时 sshd 与相关进程全部清理。
5. vim/edit 用例覆盖"打开—编辑—保存—退出"完整链路。
6. 连续 20 次会话无句柄/线程泄漏；输出泵不丢字节（大输出用例验证）。

## 8. 风险与开放问题

- vim/edit 是外部程序，版本/配置（vimrc、插件）会影响屏幕内容。需要最小化
  环境（`-u NONE`、关闭语法高亮等）并在断言上使用稳定的最小特征。
- sshd 需要管理员权限才能安装/注册服务；测试必须在"服务已存在"时才能运行，
  不能自动提权。若只能以普通用户 `sshd -d`（调试模式）运行，需改为每用例
  启动一个 foreground sshd 实例。
- 管道容量有限：输出泵必须持续读，否则大输出用例会因被测程序阻塞而超时，
  这是测试基础设施问题，不能归因为产品 BUG。
- 屏幕模型只实现必要子集；遇到未支持的序列应显式报"模型不支持"而不是静默
  忽略，避免断言假阴性。

# 计划 B：GetConsoleWindow 伪窗口

## 1. 背景

`GetConsoleWindow` 返回与当前控制台关联的窗口句柄。真实 conhost 有一个可见窗口；
corehost 的两种运行形态都没有：defterm 形态把会话交给 WindowsTerminal（终端窗口
属于 WT），conpty 形态只做 VT 转发。部分控制台程序依赖这个句柄做交互：

- 用 `SendMessage`/`PostMessage` 发窗口消息（最小化、置顶、关闭、菜单命令）；
- 用 `GetWindowRect` 估算可用尺寸；
- 用 `SetWindowText` 改标题、`ShowWindow` 控制显示；
- 用 `GetWindowThreadProcessId` 找到窗口所在线程，做 UI 自动化或输入注入；
- 找不到窗口时退化为无窗口行为（少数程序无法工作）。

当前 API 实现直接把进程内的 `GetConsoleWindow()` 结果返回；corehost 不是 GUI
进程、没有窗口，因此返回空句柄，依赖方拿到 NULL 后行为未定义或退化。

## 2. 目标

为每个控制台会话提供一个**不可见的伪窗口**：句柄有效、能被消息寻址、能接收并
响应依赖方会发的消息；窗口本身不显示任何内容，不参与渲染；窗口运行在独立线程，
并作为输入源之一融入阶段 A 的等待模型。

"不可见"不是"不存在"：调用方必须能通过句柄同步/异步发消息并得到合理结果，
`GetWindowRect`、`GetWindowThreadProcessId`、`IsWindow` 等查询类调用不能失败。

## 3. 必须先回答的问题（原版分析清单）

阶段 B1 只做分析，不允许写实现。需要从 `terminal/` 的原版窗口代码和 corehost 的
调用场景中回答：

1. 窗口类：类名、注册时机、窗口过程、类样式；窗口标题从哪里来。
2. 创建：哪个线程创建、创建时机（会话建立前/后）、父窗口、样式
   （`WS_POPUP`/`WS_OVERLAPPEDWINDOW`/`WS_VISIBLE`）、初始位置与尺寸、
   扩展样式。
3. 消息面：依赖方实际会发哪些消息；哪些是查询（`GetWindowRect`、`GetClientRect`、
   `GetWindowLongPtr`、`GetWindowText`），哪些是状态改变（`ShowWindow`、
   `SetWindowPos`、`SetWindowText`、`SetWindowLongPtr`），哪些是生命周期
   （`WM_CLOSE`、`WM_DESTROY`、`WM_QUERYENDSESSION`），哪些是输入/激活
   （`WM_SETFOCUS`、`WM_ACTIVATE`、`WM_MOUSEACTIVATE`、`WM_NCHITTEST`）。
4. 每个消息在原版的行为与返回值：必须区分"真正影响控制台状态"与"仅为交互而
   存在"的部分。窗口不可见时，大部分交互消息应当返回"什么都不做"。
5. 关闭语义：`WM_CLOSE`/`WM_SYSCOMMAND SC_CLOSE` 如何映射到控制台关闭事件；
   是否有 `CTRL_CLOSE_EVENT`；进程组如何结束。
6. 与输入的关系：原版把鼠标/焦点消息喂给输入队列；在不可见伪窗口下是否仍需
   要（答案很可能是只保留最小集：键盘事件由 VT 输入负责）。
7. 多会话：一个进程内是否可能有多控制台；每会话一个窗口还是每进程一个。
8. UI 自动化：原版暴露 UIA provider；依赖 UI 自动化的测试需要什么最小支持。
9. 标题/图标：`SetConsoleTitle` 是否要反映到窗口标题；图标是否需要。
10. 尺寸/DPI：`GetWindowRect` 返回什么尺寸（字符尺寸 × 字体，还是屏幕坐标）；
    DPI 变化时窗口线程是否需要响应。

结论必须写成 `design/0002` 的"需求规格"，每一项给出"原版行为 / 依赖方期望 /
corehost 是否需要"。

## 4. 需求规格（待 B1 后细化，下列为下限）

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| B-R1 | `GetConsoleWindow` 返回非 NULL 且进程内唯一、稳定的句柄 | 连续调用返回同一句柄；`IsWindow` 为真 |
| B-R2 | 句柄所属线程是专用窗口线程，`GetWindowThreadProcessId` 返回该线程 | 线程 id 稳定且能被枚举到 |
| B-R3 | 窗口不可见：不显示、不抢前台、不出现在任务栏、不接收真实鼠标键盘输入 | 会话运行期间无可见窗口；不改变前台窗口 |
| B-R4 | 同步消息不挂起调用方：窗口线程必须及时处理消息并返回 | 100 次同步消息往返总耗时 < 1s；无超时 |
| B-R5 | 查询类消息返回自洽结果（矩形、样式、标题），不返回垃圾 | 矩形非零且与配置尺寸一致；标题为控制台标题 |
| B-R6 | `WM_CLOSE` 映射为控制台关闭（会话结束 + 客户端收到关闭事件），语义与真实控制台一致 | 发 `WM_CLOSE` 后在超时内会话退出、客户端收到关闭事件 |
| B-R7 | 窗口在会话结束时销毁，线程退出并 join；无 USER/GDI 句柄泄漏 | 100 次会话后句柄数稳定 |
| B-R8 | 消息处理不直接修改主线程状态：需要状态变化时投递命令并等待确认 | 代码审查 + 并发压力无崩溃 |
| B-R9 | 未知消息走默认处理，不吞掉、不崩溃 | 逐一发消息清单验证 |

## 5. 与 I/O 模型的集成

- 窗口线程是第四个输入源：主线程等待集加入"窗口命令就绪"事件；窗口线程把
  需要在主线程执行的动作（例如"关闭会话"、"更新标题"）放入命令队列。
- 反过来，主线程需要窗口信息时（例如 `GetWindowRect` 依赖当前尺寸）通过
  "请求 + 完成事件"同步；禁止窗口线程直接读写控制台状态。
- 退出顺序：主线程决定退出 → 通知窗口线程销毁窗口并退出消息循环 → join →
  其余输入线程按 `plan/01` 的顺序处理。窗口线程不能先于主循环消失，否则依赖方
  可能向已销毁窗口发消息（返回失败可以接受，崩溃不可以）。

## 6. 失败模式与处理

| 场景 | 处理 |
| --- | --- |
| 注册窗口类失败（类已存在/权限） | 致命错误：无法满足 API 语义，记录错误码后终止会话 |
| 创建窗口失败 | 致命错误（同上） |
| 窗口线程创建失败 | 致命错误 |
| 窗口线程收到未知/畸形消息 | 默认处理，级别 2 日志 |
| 会话退出时仍有依赖方在发消息 | 窗口销毁前不阻塞；`SendMessage` 失败由调用方处理 |
| 依赖方在 UI 线程同步等待窗口线程、而窗口线程又在等待主线程 | 禁止窗口线程同步等待主线程；需要状态时用快照或异步命令 |

## 8. 验收标准

1. 外部客户端程序调用 `GetConsoleWindow` 得到非 NULL；`IsWindow`、
   `GetWindowThreadProcessId`、`GetWindowRect`、`GetWindowText` 返回合理值。
2. 用 `SendMessageTimeout(..., 1s)` 对消息清单逐条发送，无一条超时；未知消息
   不崩溃。
3. `WM_CLOSE` 能在 2 秒内结束会话，客户端收到关闭事件；重复发送不重复关闭。
4. 会话空闲时窗口线程阻塞在消息等待上（无轮询）；CPU 占用可忽略。
5. 连续 100 次建立/销毁会话，USER 对象与 GDI 对象数量不增长，线程数回到基线。
6. 窗口不可见：全程无窗口出现在屏幕上，前台窗口不变。
7. 阶段 C 的 defterm 用例中"用 `GetConsoleWindow` 发消息"的路径可用。

## 9. 风险与开放问题

- 依赖方可能用 `FindWindow`/`EnumWindows` 按类名或标题查找窗口：消息专用窗口
  （`HWND_MESSAGE`）不会被枚举到。是否必须做成可枚举的顶层窗口，取决于
  B1 对真实调用方的调查结论，记录在 `design/0002`。
- "不可见"与"可最小化/最大化"存在语义冲突：`ShowWindow` 调用是否要真的改变
  窗口状态（影响 `IsWindowVisible`、`GetWindowPlacement`）需要在 B2 决定。
- defterm 形态下 WT 才是真实终端：伪窗口只服务于"需要 hwnd 的程序"，不应
  尝试把 WT 的窗口行为复制过来。
- UI 自动化支持的成本可能远超收益：如果只用于测试，测试应优先用消息而不是
  完整 UIA provider。

# 计划 A：非轮询 I/O 模型

## 1. 现状与问题

corehost 的会话有一个主循环，同时服务四类事件：ConDrv 消息、终端输入字节、
WT 信号管道、以及退出条件。当前实现用"短超时等待 + 主动窥探"把四类事件揉在
一起：

- 主循环在没有 ConDrv 消息时按固定时间片（约 16ms）等待一次，醒来后主动
  `PeekNamedPipe` 窥探终端输入与信号管道。
- 有挂起读请求时，同样按固定时间片轮询，醒来后先窥探信号管道再窥探输入管道。
- 初始 CONNECT 循环重复了同一套时间片等待。
- 窥探结果为空只代表"此刻没有数据"，于是下一轮继续等下一个时间片。

后果：没有输入时线程仍然每 16ms 唤醒一次；输入延迟下限等于时间片；空闲 CPU
占用与时间片绑定；时间片一旦调大，键盘响应与 resize 响应都会变慢。这不是
"等待输入"，而是"定期检查输入"。

## 2. 目标语义

定义"输入"为：ConDrv 有新消息、终端输入有新字节、信号管道有新消息、窗口
消息队列有新消息（阶段 B 引入）、或任一输入源关闭。

目标：**没有输入时，所有线程都阻塞在无限等待上；有输入时，只有该输入源
对应的线程被唤醒，并在会话锁内同步完成处理（不排队、不异步）。**

推论（必须成立的不变式）：

1. 不存在固定超时的周期性唤醒，也不存在任何"等待上限/超时兜底"：所有等待
   要么是无限等待（由事件唤醒），要么由取消协议保证必然返回。产品代码里不允许
   以超时"放弃等待"（原因见 `design/0001` 4.6）。
2. 终端输入线程在 `ReadFile` 上阻塞，而不是"先窥探、没数据就睡"。
3. 主线程在"任一输入源状态可能变化"的事件上无限等待，不自行轮询。
4. 关闭/退出由状态驱动，不靠"多等一个时间片再看一眼"。
5. 控制台处理保持同步：任何输入一旦被读取就立即处理完，不存在"事件先入队、
   稍后处理"的异步阶段，也不存在需要排空的应用层队列。

## 3. 输入源与线程职责

| 输入源 | 数据形态 | 线程职责 | 处理方式 |
| --- | --- | --- | --- |
| ConDrv `\Server` | 4KB 消息（描述符 + body），非阻塞 READ_IO，靠 InputAvailableEvent 通知 | 保留在主线程：READ_IO 仍由主线程发起（消息完成需要控制台状态） | 主线程在会话锁内消费 |
| 终端输入 `vt_in` | UTF-8 字节流，可能被管道边界切开 | 独立线程：阻塞读、解码、VT 解析、键盘事件生成、cooked 行编辑 | 读到数据后在会话锁内**立即处理**，不排队 |
| WT 信号管道 | 定长消息（id + payload），写端一次一条 | 独立线程：阻塞读、协议校验、执行 resize/clear/parent/show | 同上；状态变更在锁内完成 |
| 窗口消息（B） | Win32 消息 | 独立线程：消息循环，处理同步请求 | 需要控制台状态的动作在锁内完成，不跨线程等待 |
| 客户端输入可用事件 | 驱动 SetEvent | 不作为线程；只作为主线程等待集的一员 | 主线程 |

控制台状态由会话锁保护：`console_state`、主/备用 `screen_buffer`、
`input_buffer`、ConDrv pending 请求、VT 输出缓冲、光标与边界追踪，只能在持有
会话锁时访问。输入线程的私有状态（解码器、解析器、行缓冲）不属于共享状态，
因此不需要锁，也不需要交给主线程。

## 4. 状态与缓冲归属矩阵

迁移要求来自 agent.md："每个线程拥有自己的输入缓冲区和状态（需要从现有控制台
状态对象移动到线程自己的对象）"。逐项归属如下，实现时必须能对上这张表：

| 数据 | 迁移后归属 | 访问约束 |
| --- | --- | --- |
| `vt_in` 原始读缓冲、跨请求残留字节 | 输入线程 | 线程私有，无锁 |
| UTF-8 增量解码器（跨读边界半字符） | 输入线程 | 线程私有 |
| VT 输入解析器及其原文缓冲 | 输入线程 | 线程私有 |
| 键盘修饰键状态、Win32 Input 解码状态 | 输入线程 | 线程私有 |
| cooked 行缓冲与行内编辑光标 | 输入线程 | 线程私有 |
| 输入侧 EOF/关闭标志 | 共享 | 会话锁内读写 |
| Console API 可见的 `INPUT_RECORD` 队列 | 共享 | 会话锁内写（主线程读 API 时同样持锁） |
| ConDrv 挂起请求（raw/cooked/peek 三类） | 共享 | 会话锁内访问 |
| 屏幕缓冲区、视口、光标、属性、CP、标题 | 共享 | 会话锁内访问 |
| 终端光标/行编辑边界的本地追踪 | 共享 | 会话锁内访问 |
| VT 输出字节缓冲 | 共享 | 会话锁内访问，flush 也在锁内（现状相同） |
| 信号消息解析过程中的半条消息 | 信号线程 | 线程私有 |
| 窗口句柄与窗口过程状态 | 窗口线程 | 见 `plan/02` |

关键取舍：行编辑（cooked）在输入线程完成，回显也在同一线程、同一会话锁内
写入 VT 输出缓冲。因为处理是同步的，按键回显与程序输出的顺序由锁的获取顺序
决定，与单线程时代的语义一致；不需要"回显动作 + 主线程渲染"的两段式设计。

## 5. 等待与唤醒协议

1. 会话锁（独占 SRWLock）保护全部控制台共享状态；任何线程只在锁内推进状态。
2. 输入线程读到数据后：取锁 → 同步处理（解析、行编辑、更新 `input_buffer`、
   完成 pending 请求、写回显）→ 解锁 → 继续阻塞读。处理期间不排队、不暂存。
3. 输入线程在**解锁后**置位本源的"状态变化"事件；事件只表示"状态可能变了"，
   不携带数据，因此重复置位无副作用，也没有可累积的队列。
4. 主线程等待集 = {ConDrv InputAvailableEvent，各输入源状态变化事件}，无超时；
   醒来后取锁、把 READ_IO 读到"无消息"为止、处理消息、解锁，再回到等待。
5. 丢失唤醒不可能：工作线程先改状态再置位；主线程醒来后只依据真实状态判断，
   不依赖事件内容。事件若在主线程等待前已置位，等待立即返回。
6. 背压来自管道本身：输入线程只有处理完上一块数据才会读下一块，因此最多只有
   一块数据在途，不存在"生产者快于消费者导致累积"的问题。

## 6. 退出协议

三条退出路径都必须 join 全部线程：

| 路径 | 触发 | 步骤 |
| --- | --- | --- |
| 正常 EOF | `vt_in` 关闭；或信号管道关闭 | 输入线程发布 EOF 事件并退出 → 主线程完成挂起读、flush 输出 → 通知其余线程停止 → join |
| 服务端断开 | ConDrv 返回断开 | 主线程通知所有输入线程停止 → 取消阻塞读 → join → flush |
| 强制关闭 | 外部关闭会话/进程即将退出 | 同服务端断开：置停止标志、取消阻塞读、无限 join。不允许"等一会儿放弃等待"的兜底；任何无法唤醒的线程都是致命错误 |

停止机制：

- 每个线程有独立的停止事件；线程在进入阻塞读之前检查一次，阻塞期间被取消
  后再次检查。
- 阻塞在 `ReadFile` 上的线程用"取消同步 I/O"打断；由于存在"检查停止标志"与
  "真正进入读"之间的窗口，取消必须重复执行，直到线程确认退出（细节与原因见
  `design/0001`）。
- 窗口线程用投递退出消息的方式结束消息循环。
- 主线程负责所有 join，顺序固定：先停生产者（输入线程），再停主循环，最后
  释放句柄；任何线程都不能在 join 之前析构它引用的状态。
- join 是无限等待。终止性由"停止标志 + 可取消阻塞读 + 取消重试"保证，而不是
  由超时保证；破坏了终止性的情况（取消返回意外错误、线程不响应停止）按致命
  错误处理并记录线程名与状态。

## 7. 错误分类

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 预期失败（非致命） | 管道暂无数据、对端关闭、读被取消、短读、驱动返回"无消息" | 返回值/状态枚举，调用方据此推进状态 |
| 协议损坏（非致命→会话级失败） | 信号消息长度不足、未知信号 id | 记录诊断、按会话结束处理，不抛到无关路径 |
| 致命 | 本不应失败的系统调用失败（创建线程/事件/句柄、提交完成、取错误码失败）、OOM、不变量破坏 | 主线程抛异常；工作线程 `std::abort()`；日志必须包含函数、错误码、线程名 |
| 编程错误 | completion 与 descriptor 不匹配、状态机非法迁移 | 断言（Debug）或致命错误（Release 也保留检查） |

禁止 `catch`：因此工作线程内不允许"抛出去让主线程接"的设计；线程内致命错误
直接 abort，这是刻意选择，记录在 `design/0001`。

所有可能失败的调用都必须检查返回值。审查时以"函数签名是否可能失败"为准，
不因为"这里应该不会失败"而忽略——"本不应失败却失败"正是致命错误的定义。

## 8. 锁与条件变量

- 只使用 `common/win32` 新增的 SRWLock 封装：共享/独占锁 + 条件变量。
- 会话锁以独占方式使用；封装要求：RAII、不可拷贝、带谓词的限时等待。
- 锁内禁止阻塞等待（句柄等待、阻塞读、条件变量等待、join）；只允许短同步调用。
- 只有一个会话锁，因此没有锁序问题；禁止在锁内回调或递归获取。
- 不需要锁的数据显式标注"仅某线程访问"，并在类型注释中写清，防止后续误用。
- 条件变量只用于"状态变化需要唤醒等待者"的场合；跨线程的唤醒优先用事件 +
  真实状态复读，不依赖事件内容。

## 9. 可观测性

- 日志：线程启动/退出、等待集变化、EOF/断开、取消读、join 结果，必须打点；
  高频路径用级别 3。
- 计数器（Debug 或级别 3）：主循环唤醒次数、每源事件数、空转次数、每次唤醒
  处理的事件数。用于验证"无输入不唤醒"。
- 线程名：每个工作线程有稳定、可区分的中文/英文短名，便于调试器与 ETW 识别。

## 10. 验收标准

阶段 A 结束时必须能给出下列证据：

1. 代码审查：I/O 主循环、输入路径、信号路径中不存在固定 16ms 等待；不存在
   "窥探—睡眠—再窥探"循环；`grep` 结果作为证据。
2. 空闲：会话空闲 30 秒，主循环唤醒次数 = 0（除首次），进程 CPU 时间增长
   接近 0（记录实测值）。
3. 时延：输入一个字符到回显的延迟不劣于改造前（同一测试方法，记录 P50/P95）。
4. 功能不回归：现有 `ctest` 全绿；键盘（含 Win32 Input、Ctrl 组合、功能键）、
   cooked 行编辑（退格、Ctrl+C、Ctrl+Z）、粘贴多字节、CPR 继承光标、resize
   全部保持原行为。
5. EOF：关闭终端/写端后 1 秒内退出，退出码符合预期，无残留线程。
6. 断开：服务端断开后 1 秒内退出，不等待用户输入。
7. 压力：连续 100 次"启动—输入—退出"会话，句柄数不增长，无线程泄漏。
8. 稳定：同一套输入脚本重复 20 次，输出与退出码完全一致（无竞态导致的抖动）。
9. 同步性：代码中不存在输入事件队列/延迟处理；输入线程处理完一块数据才读下一
   块（背压成立）；用"大量输入 + 慢消费"压力场景验证无累积、无内存增长。

## 12. 风险与开放问题

- 回显在输入线程锁内直接写输出，与应用程序输出的顺序由锁保证；仍需 A4 用
  对照测试确认与单线程时代的行为一致。
- 锁内 `WriteFile` 可能在终端不读时阻塞，从而阻塞其他输入线程；A6 评估是否
  改为"锁内追加、锁外写"（仍是同步语义，只是不在锁内做可能阻塞的写）。
- 取消阻塞读在极窄窗口下的可靠性，需要在 A8 用注入延迟的压力测试验证；
  验证目标是"无限 join 一定返回"，而不是"超时后放弃"。
- `Ctrl+Z`、`Ctrl+C` 的语义依赖输入模式；输入线程在锁内直接读模式状态，不需要
  快照（见 `design/0001` 4.5）。

# 设计取舍 0001：I/O 模型的线程结构与状态归属

状态：已决定（实现待验证项见文末）

## 1. 背景

见 `plan/01-io-model.md`。核心矛盾：多个输入源（ConDrv 消息、终端输入管道、
信号管道、窗口消息）需要同时被服务，而控制台状态（屏幕、光标、输入队列、
ConDrv 挂起请求、VT 输出）必须单线程访问。当前用一个线程加短超时轮询把两者
凑在一起，导致空转与延迟下限。

## 2. 候选方案

### 方案 A：每源一线程 + 主线程唯一状态写者（选定）

- ConDrv 仍由主线程 `READ_IO`（因为消息处理依赖全部控制台状态）。
- 终端输入、信号、窗口各一个线程，阻塞在自己的句柄/消息上；解析与私有缓冲
  在线程内，事件经队列交给主线程。
- 主线程等待集 = {ConDrv InputAvailableEvent, 输入就绪事件}，无限等待。

优点：符合任务要求（线程拥有自己的缓冲与状态）；控制台状态仍单写者，避免给
整个状态机加锁；事件驱动，无空转。

缺点：引入线程间事件与队列；退出时要处理"阻塞读取消"；需要小心回显/输出的
顺序。

### 方案 B：全异步 I/O（overlapped + IOCP）

否决。终端输入与信号管道由外部创建（匿名管道，`libconpty`/defterm 入口），
无法要求调用方以 `FILE_FLAG_OVERLAPPED` 打开；`DeviceIoControl` 的 READ_IO 也
是同步完成语义。强行改造需要复制句柄/自建转发管道，复杂度和风险远超收益，
且会把"输入源"变成"转发层"，违背"从真正原因解决"。

### 方案 C：保留轮询，增大时间片或改成自适应

否决。问题的本质是"没有输入也定期醒来"，调整间隔只是把空转变成延迟。

### 方案 D：给控制台状态加锁，多线程直接处理

否决。屏幕/光标/API 状态被大量路径读写，加锁会把整个处理器变成临界区；线程
与会话语义（如"当前 pending 请求"）也会变成共享可变状态，死锁概率与维护成本
都不可接受。

## 3. 选定方案的关键决定

### 3.1 主线程保留 ConDrv 循环

`READ_IO` 是"提交上一条 completion + 读取下一条消息"的复合操作，completion
内容来自控制台状态。把它放到独立线程意味着 completion 的构造要跨线程，收益
为零。因此 ConDrv 线程不做，主线程做；主线程在 InputAvailableEvent 与输入就绪
事件的等待集上无限等待，醒来后先把 READ_IO 排空（读到"无消息"为止），再排空
输入事件队列。

### 3.2 事件与队列协议

- 每个输入线程有一个有界事件队列（SRWLock 保护），入队后 Set 同一个
  "输入就绪"自动重置事件。
- 主线程醒来后：取锁、整批交换出队列、解锁、处理；循环直到队列空；然后处理
  ConDrv；再回到等待。自动重置事件 + "排空到空"保证不丢唤醒（若入队发生在
  排空之后、等待之前，事件已置位，等待立即返回）。
- 队列满按致命错误处理（说明主线程长期不推进），带线程名与计数终止，而不是
  丢弃输入。

### 3.3 输入状态迁移与回显归属

任务要求"每个线程拥有自己的输入缓冲区和状态"。迁移清单见 `plan/01` 第 4 节。

回显（用户按键在终端上的显示）不由输入线程格式化 VT，而是产出语义动作：

| 动作 | 参数 | 主线程渲染 |
| --- | --- | --- |
| `echo_text` | UTF-8 文本 | 追加到 VT 输出缓冲，更新终端光标追踪 |
| `erase` | 字符数/行 | 发送退格/空格/重画 |
| `redraw_line` | 当前行文本 + 光标列 | 回到行首、重画、定位光标 |
| `newline` | — | 换行 + 回车 |
| `bell` | — | `\a` |

理由：回显的坐标依赖 `terminal_cursor_state`，而该状态同时被应用输出路径
（`sync_cursor_after_write`）修改；把它留给主线程就避免了跨线程共享与锁。输入
线程只做"行内容与光标在行内的位置"这类纯文本编辑状态，不关心终端坐标。

### 3.4 输入模式的快照

`Ctrl+Z` 是否算 EOF、`Ctrl+C` 是否产生信号，取决于当前输入模式（主线程状态）。
决定：主线程在模式变化时发布一份只读快照（原子替换的不可变结构，或带版本的
小结构 + 事件），输入线程只读快照；不要求输入线程回读主线程状态。快照过期
最多影响"模式变化与下一次按键"之间的极窄窗口，这是可接受的（与真实控制台在
模式切换时的行为一致）。

### 3.5 阻塞读的取消

匿名管道不支持 overlapped，也没有"可等待的可读事件"。选定 `CancelSynchronousIo`
方案：

1. 线程进入 `ReadFile` 前在锁内置位 `in_read`，返回后清除。
2. 主线程请求停止：置停止标志，然后循环"若 `in_read` 置位则取消同步 I/O；等待
   5ms"直到线程发出退出信号。
3. 被取消的 `ReadFile` 返回 `ERROR_OPERATION_ABORTED`，线程检查停止标志后正常
   退出（不当作 EOF，不产生输入事件）。
4. 循环而不是只取消一次，是为了覆盖"线程已通过停止检查、尚未进入 ReadFile"
   的窗口；只要主线程持续观察到 `in_read` 并再次取消，就不会永久阻塞。
5. 兜底：join 等待设上限（例如 2s），超时视为致命错误（记录线程名与状态后
   终止进程）。正常情况下不会触发。

被否决的替代：关闭读端句柄打断读（行为未定义，可能让 I/O 继续挂起）；把读端
改成消息模式/overlapped（调用方给的句柄，不可控）；`TerminateThread`（破坏
进程状态，任务明确要求"正确处理线程退出"）。

### 3.6 致命错误不能跨线程抛出

任务要求"致命错误抛出异常或 `std::abort()`，不要捕获异常"。异常无法跨线程
传播，因此：主线程致命错误 → 抛 `win32::error`/`std::bad_alloc`；工作线程致命
错误 → 记录诊断后 `std::abort()`。全仓库不新增 `catch`。

### 3.7 锁

新增 `common/win32` 的 SRWLock 封装：`shared_lock`/`exclusive_lock` RAII +
`condition_variable`（带谓词等待与超时）。规则：

- 队列锁是叶子锁；持锁期间不做系统调用、不写日志、不分配。
- 不需要锁的数据在类型注释中显式写"仅 X 线程"。
- 条件变量只用于"状态变化等待"，纯生产/消费用队列 + 事件。
- 锁序：会话状态（主线程独占，无需锁）→ 各线程队列锁。禁止反向获取。

### 3.8 线程命名

每个工作线程在入口处设置可读名称（终端输入 / 信号管道 / 控制台窗口 + 会话
标识）。`common/win32` 提供统一的设置函数，避免每个线程各写一套。

## 4. 影响

- 输入解析、行编辑、信号处理从 `pipe_bridge` 中拆出，`pipe_bridge` 变成"主线程
  侧的输入状态与 API 状态持有者"。
- 主循环从"时间片 + 窥探"变成"等待集 + 排空"。
- defterm 的初始 CONNECT 循环与 handoff 等待循环同步改造，否则会留下第二套
  轮询。
- 需要新的单元测试（锁、线程、取消）与基于会话的回归测试。

## 5. 待验证 / 开放问题

1. 回显动作队列与应用输出的严格顺序：需要对照测试；若出现顺序差异，考虑把
   "输入回显"也放进主线程的输出序列点统一排序。
2. 取消协议的可靠性需要注入延迟（让线程卡在"检查后、读前"）的压力测试验证。
3. 事件队列上限与批量大小的实测取值。
4. 输入模式快照的发布频率（每次 SetConsoleMode 都发布，还是按需）对性能的
   影响可忽略，但需要避免 ABA 式的陈旧快照。
5. 信号管道消息（resize）与输入事件的相对顺序是否需要严格保证（当前实现里
   resize 先于输入处理）。
